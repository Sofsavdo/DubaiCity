# BANDLY — Authentication, Account and Privacy Specification

## 2. Principles

1. **No raw secrets at rest.** Session tokens, legacy tokens, OTP codes and API secrets are stored only as hashes/HMACs. Raw values exist in memory and on the user's device.
2. **Identity by stable subject, never by email text.** Google and Telegram accounts are bound by their immutable subject id.
3. **Server decides.** Age band, plan, credits and roles come from the database, never from request fields.
4. **Defence in depth** for isolation: application scoping + database-level policies.
5. **Data minimisation.** Collect only what a feature needs; voice audio is not stored.

## 3. Email one-time code (OTP)

| Item | Specification |
|---|---|
| Flow | `POST /auth/email/start {email}` → `POST /auth/email/verify {email, code}` → session |
| Code | 6 digits from a CSPRNG; **single use**; TTL **10 minutes** |
| Storage | `auth_challenges(id, purpose, email_norm, code_hmac, attempts, expires_at, consumed_at, ip_hash)`; `code_hmac = HMAC-SHA256(server_secret, challenge_id ‖ email_norm ‖ code)`. The code itself is never stored or logged |
| Verification | Constant-time compare; **max 5 attempts** per challenge, then the challenge is dead; verification consumes the challenge atomically (`UPDATE … SET consumed_at=now() WHERE consumed_at IS NULL AND expires_at>now() RETURNING`) so concurrent submissions cannot reuse a code |
| Rate limits | Start: ≤ 5 per email per hour, ≤ 30 per IP per hour, 60 s resend cooldown. Verify: ≤ 10 per IP per 10 min. Limits stored server-side (not in process memory) |
| Enumeration | Identical response and timing for known and unknown email addresses |
| Normalisation | Trim, lower-case the domain, reject control characters; plus-addressing kept (not collapsed) |
| Delivery | Transactional email provider (**[U] U-3**); SPF, DKIM and DMARC configured on the sending domain. Delivery failures are shown as "try again", never as success |
| Abuse | Disposable-domain deny-list optional; CAPTCHA fallback after repeated starts from one IP |

Magic links are not proposed: they add phishing/prefetch risks (mail scanners can consume one-time links).

## 4. Google and Telegram

### 4.1 Google (OpenID Connect)
- Authorization-code flow with **PKCE** and `state` + `nonce`; redirect URI allow-listed.
- Server verifies the ID token: signature against Google's published keys (cached with expiry), `iss`, `aud` = our client id, `exp`, `nonce`.
- Identity key = `sub`. `email` is used only if `email_verified = true`, and only to *suggest* linking.
- **Linking rule:** an existing account is linked to a Google identity only when the user is **already authenticated** (session or fresh OTP). Matching by email alone, without proof of control of the existing account, is forbidden (account-takeover vector).

### 4.2 Telegram
Two surfaces, both validated server-side:
- **Login Widget:** verify the `hash` as `HMAC-SHA256(data_check_string, SHA256(bot_token))`; reject if `auth_date` is older than 5 minutes; keys sorted, `hash` excluded from the string.
- **Mini App (`initData`):** verify with the Mini-App scheme (`HMAC-SHA256` using the key derived from the literal `WebAppData` and the bot token); same freshness rule.
- Identity key = Telegram numeric user id. The bot token is a server secret.
- Telegram supplies no verified email; such accounts are encouraged (not forced) to add one for recovery.
- **[U]** The exact current field names and verification string format must be re-checked against Telegram's documentation at implementation time; this specification describes the mechanism, not a copied reference implementation.

### 4.3 Table: identities
`user_identities(user_id, provider ∈ {email, google, telegram}, subject, verified_at, created_at)` with `UNIQUE(provider, subject)`. For `email`, `subject` is the normalised address. **Legacy tokens are not identities** (§6).

## 5. Sessions

| Item | Specification |
|---|---|
| Token | 256-bit CSPRNG value; delivered in an **`__Host-` prefixed cookie**: `HttpOnly; Secure; SameSite=Lax; Path=/` |
| Storage | `sessions(id, user_id, token_hash CHAR(64) UNIQUE, created_at, last_seen_at, expires_at, absolute_expires_at, revoked_at, ip_hash, user_agent_hash, kind ∈ {web, legacy, device})`; `token_hash = SHA-256(token)`. Never log or return the token after creation |
| Lifetime | Sliding idle expiry **30 days**; absolute expiry **90 days**; `last_seen_at` updated at most once per hour to limit writes |
| Revocation | Per session; "sign out everywhere"; automatic revoke-all on email change, on identity unlink, and on account deletion. Revocation takes effect on the next request because every request looks the session up (no stateless JWTs) |
| Rotation | New token issued after login, after linking an identity, and after privilege-sensitive actions |
| CSRF | Cookie auth ⇒ state-changing requests require a custom header (`X-Bandly-CSRF`, value bound to the session) **and** an `Origin`/`Sec-Fetch-Site` check; `GET` never mutates |
| CORS | Same-origin only; no wildcard |
| Device binding | Not enforced (would break legitimate mobile network changes); anomalies logged |
| Bearer transport | A `Authorization: Bearer` path exists for future native apps and for the **legacy transition** (§6); tokens must never appear in URLs |

## 6. Legacy account migration

| Item | Specification |
|---|---|
| Storage | `user_credentials(kind='legacy_token', hash = SHA-256(token), user_id, created_at, last_used_at, expires_at)`. **The raw token is never stored in the new database and is never used as an identity subject.** |
| Acceptance | A request with a legacy token (header or body) is hashed and matched; success creates a normal server session (`kind=legacy`) and sets the cookie, so subsequent requests no longer send the token |
| Prompting | After first use, the account page asks to attach an email/Google/Telegram identity ("protect your progress and subscription") |
| Sunset | Legacy credentials expire **90 days** after the M3 release **or** immediately after the user attaches a verified identity (whichever first). Reminders at 30/7 days require an email, so for unattached accounts the in-app prompt is the only channel — **[U]** acceptable loss rate for abandoned accounts to be decided by the owner |
| Tokens already in the wild | Shared "account codes" copied by users are equivalent to passwords; after attachment, the legacy token is revoked, closing any previously copied code |
| Removing the copy-code feature | The "copy account code" button is removed in M3; attached accounts never see a raw token |
| Nickname conflicts | Legacy nicknames are preserved as `handle` (unique, case-insensitive). New users choose a handle at sign-up; handle changes are rate-limited and uniqueness is enforced |
| Audit | Each legacy login and conversion is logged (user id, time, outcome), never the token |

## 7. User data isolation

1. **Application layer:** every query takes the user id from the **session**, never from the request body or query string. Resource ids (attempt, submission, plan) are always joined to `user_id = session.user_id`; a mismatch returns `404`, not `403`.
2. **Database layer (defence in depth) [R]:** PostgreSQL Row-Level Security on all user-owned tables with `USING (user_id = current_setting('app.user_id')::uuid)`; each request runs in a transaction that sets `app.user_id` with `SET LOCAL`. The application's database role is not a superuser and cannot bypass RLS; admin tooling uses a separate role.
3. **Automated tests:** for every endpoint taking a resource id, a cross-user test asserts `404` and no data leak (the pattern already used for payments in `server/payments.test.ts`). A test enumerates all routes and fails if a route is neither on the public allow-list nor covered by an isolation test.
4. **Public data:** leaderboards and duels expose only `handle`, XP and rank; never email, age band or identity ids.
5. **Admin:** role-based (`roles` table), per-admin credentials via the same session mechanism with mandatory second factor (**[R]**), every action written to an append-only `audit_log`. The static shared admin token is removed.

## 8. Age and minors

| Item | Specification |
|---|---|
| Collection | Date of birth (month and year suffice for banding; full date if the legal basis requires it) at sign-up; stored as `birth_year`/`birth_month` and a derived `age_band` |
| Bands | `child` (< min age), `minor` (min age – 17), `adult` (≥ 18). The **minimum age depends on market and law (13/14/16 are all used)** — **[U] U-7**; the system takes it from configuration per country |
| Child | No account is created; a message explains how a parent may contact the service. Parental-consent flows are out of scope for Phase 1 |
| Minor | Server-enforced: Savage Coach and mild profanity unavailable regardless of client flags; filtered vocabulary set; no marketing email; no public leaderboard display name beyond the handle; AI chat transcripts retained for a shorter period |
| Adult | May opt in to adult personality modes; opt-in stored server-side with timestamp |
| Verification honesty | **Age is self-declared.** The system cannot verify it without identity documents, which is not proposed. The product therefore must not claim "verified adult". Enabling the profanity mode on a self-declared basis is a business risk (**OWNER_DECISIONS D6**) |
| Changes | A minor reaching 18 is moved to the adult band by a scheduled job; users cannot lower their band without support action (audit-logged) |
| Existing users | Legacy users have no age. Until they provide it they are treated as **minor** for adult-only features. This changes the current behaviour of the 18+ checkbox, which is client-side only |

## 9. Account deletion and data export

### 9.1 Deletion
- Self-service: "Delete my account" → confirm with a fresh OTP/Google/Telegram check → `deletion_requests(user_id, requested_at, effective_at = +14 days, status)`; account is deactivated immediately (sessions revoked, hidden from leaderboards) and **recoverable** for 14 days.
- At `effective_at` a job:
  - hard-deletes: sessions, credentials, identities, profile, learner state (mastery, plans, attempts, answers), writing submissions, speaking transcripts, AI evaluations, XP history, achievements;
  - **anonymises** records that must be kept: `payments` (keep amounts, dates, provider references; replace `user_id` with a tombstone id) and `usage_records` (cost accounting; user id → tombstone);
  - removes the user's rows from leaderboard snapshots and duel result displays (duel counterparts keep their own result).
- **Backups** are not rewritten; deleted data ages out when backups expire (maximum **35 days**; stated in the privacy notice). A restore from backup must re-apply the deletion log before any data is served (`deletion_log` is kept outside user tables and re-applied by the restore runbook).
- Active paid subscription: the user is told that deletion ends access without a refund unless the refund policy says otherwise (**[U]** policy is an owner decision).
- Payment-record retention: legally required periods vary by country (**[U] U-6**).

### 9.2 Export
- "Download my data" produces a machine-readable archive (JSON, plus CSV for results) containing: profile, identities (provider and masked subject), age band, plans and payments, learner profile, mastery, error history, vocabulary state, attempts and answers, writing submissions, transcripts (if retained), AI evaluations, XP and achievements.
- Generated asynchronously, available for 7 days at an authenticated, single-use link; at most one export per 24 h; the generation itself is logged. Secrets (token hashes, OTP data) are excluded.

## 10. Privacy and retention policy (proposed defaults)

| Data | Purpose | Default retention |
|---|---|---|
| Account, profile, learner state | Provide the service | Until deletion |
| Voice audio | **Not stored** (processed transiently by the provider; provider retention settings must be configured to the minimum and confirmed in writing) | 0 |
| Speaking transcripts and writing submissions | Feedback and progress | 24 months for adults, 12 months for minors, or until the user deletes them **[U] owner/legal to confirm** |
| AI evaluations | Progress history | Same as the submission |
| `usage_records` | Cost accounting, abuse control | 24 months, anonymised after account deletion |
| Payment records | Accounting, disputes | Statutory period (**U-6**) |
| Auth challenges (OTP) | Sign-in | Deleted 24 h after expiry |
| Sessions | Security | Deleted 30 days after expiry/revocation |
| Request logs | Security, debugging | 30 days; IPs truncated or hashed after 7 days; never tokens, OTPs, or request bodies of auth endpoints |
| Backups | Recovery | 35 days (database), per §9.1 |

A privacy notice and cookie notice in each supported language is a launch requirement (Phase 8). Third-party processors (email, AI, speech, payments) are listed with purpose and region. International transfer rules and in-country storage obligations are **[U] U-1** and require counsel.

## 11. Security controls summary

| Control | Specification |
|---|---|
| Secrets | Environment variables only; validated at start-up; never logged; rotation procedure documented; separate secrets per environment |
| Logging hygiene | Central redaction of `authorization`, `cookie`, `x-token`, `token`, `code`, `password`-like fields |
| Headers | `Content-Security-Policy` (no inline scripts), `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`, `Permissions-Policy` limiting camera/geolocation and allowing microphone for the app origin only |
| Dependency hygiene | Lockfile committed (present), automated advisory scanning in CI |
| Brute force / abuse | Rate limits stored in PostgreSQL (or Redis later), keyed by user, IP hash and route; progressive delays on repeated failures |
| Monitoring | Alerts on spikes of failed logins, OTP sends, 5xx rate, credit-reservation failures |
| Pen-test | An external review before paid launch (M8 gate) |
